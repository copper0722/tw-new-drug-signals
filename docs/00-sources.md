# 00 — 來源、端點與欄位速查

**這頁回答什麼**：每個訊號實際上要打哪裡、拿到什麼欄位、那個欄位能回答什麼、
不能回答什麼。其餘各頁不再重複端點與欄位，需要時回頭查這裡。

本頁所有數字都在 **2026-08-05** 量測。每個數字後面的 `M-NN` 是它在
[`measurements.json`](../measurements.json) 裡的登記編號——那裡有它的母體、
方法、重跑指令，以及引用它時必須一起講的話。

---

## A. 三個來源在哪裡

| # | 來源 | 型態 | 本頁 | 語意寫在 |
|---|---|---|---|---|
| 1 | 許可證明細的 `restraintItemsCode` 是否含碼 `07` | 逐證 API（POST，有節流成本） | §C | [docs/02](02-marker-restraint-07.md) |
| 2 | 食藥署〈新成分新藥核准審查報告摘要〉 | 逐案網頁清單 | §D | [docs/03](03-marker-nme-report.md) |
| 3 | 成分正規化後的 moiety 首見 | **自算**，沒有端點 | §E、§F | [docs/04](04-moiety-first-appearance.md) |
| — | ATC | 明細的 `atcList` 欄 | §C | 分類與篩選用；**不可**當新舊的鍵（`M-33`） |

**「哪個問題該用哪個訊號」的決策表只維護一份**，在
[docs/05](05-crosswalk.md)。同一張表放三個地方，遲早會有兩份是舊的。

三個都不回答「這是不是**法定**新藥」。藥事法第 7 條的新藥身分來自**審查認定**，
不是任何一個可以從許可證讀出來的欄位（[docs/01](01-what-counts-as-new.md)）。

## B. 碼表（兩張，都是封閉集合）

```
https://lmspiq.fda.gov.tw/api/public/codes/search/full/codeKind/Lic.Type
https://lmspiq.fda.gov.tw/api/public/codes/search/full/codeKind/Restraint.Dr
```

兩張都要就跑 `make codes`：它送出第一次、**等 30 秒**、再送第二次，而且用
`curl --fail`，所以 HTTP 錯誤會讓它停下來而不是把錯誤頁面寫進你的檔案。
**這件事非做不可**：`curl -s` 在 422 時仍然回傳 exit 0，把「連接次數過於頻繁」
的回應存成碼表，你會得到一份看起來很正常的空碼表（見 §C）。

| 碼表 | 筆數 | 本 repo 怎麼用 |
|---|---|---|
| `Lic.Type`（字別） | **61**（`M-01`） | 從標題抽字別時的合法集合。其中藥品類（排除醫器／粧／色）**31** 種（`M-02`）；藥品許可證資料裡實際出現過的只有 **26** 種（`M-07`）。 |
| `Restraint.Dr`（限制項目） | **91**（`M-03`） | 提供 `07`，也提供另外 7 個名稱含「監視」的碼（合計 **8** 個，`M-04`）——那 7 個是「EXACT-`07` 比對器」的負控，**不是**「這些藥不是新藥」的意思（`1L 監視中新藥`、`26 監視期滿新藥` 的名稱就含「新藥」）。 |

`M-01`／`M-02`／`M-03`／`M-04` 用隨附的碼表快照就能重跑：

```console
$ python3 reference/measure_fixtures.py M-04
8
```

`M-07`（實際出現 26 種）不行——它需要一份完整的許可證表，本 repo 不發布。
**碼表列的是可能值，出現值是另一件事，兩者不可互相引用。**

快照與重抓指令：[`fixtures/lic_type_codes.2026-08-05.json`](../fixtures/lic_type_codes.2026-08-05.json)、
[`fixtures/restraint_codes.2026-08-05.json`](../fixtures/restraint_codes.2026-08-05.json)。

碼表回傳的每筆只有兩個有用欄位：`value`（碼）與 `text`（名稱）。**沒有定義欄位。**
所以「07 是什麼意思」這件事，碼表本身答不出來；見 [docs/01](01-what-counts-as-new.md)
把法源和讀法分開的那一節。

**注意隨附快照的欄位名不同**：`value`／`text` 在快照裡存成 `code`／`lic_type`
與 `code`／`name`，因為原名讀不出是什麼。照上面這一段的欄位名去讀快照會 KeyError；
兩個快照的 `_meta.field_names` 也寫了同一件事。

## C. 逐證明細 API

```
POST https://lmspiq.fda.gov.tw/api/public/sh/piq/1000/licSearch
Content-Type: application/json

{"data": {"licBaseId": "60001328"}}
```

`licBaseId` 就是 licId，組成規則見 [docs/06](06-permit-identity-and-dates.md)。

回應的 `data` 有 40 餘個欄位。與「新／舊」判讀相關的是這幾個：

| 欄位 | 內容 | 注意 |
|---|---|---|
| `restraintItemsCode` | 字串陣列，例如 `["02 輸 入", "07 新藥監視", "5F 免除銜接性試驗"]` | 每個元素是「碼 + 空白 + 名稱」，空白可能是全形 U+3000。比對**碼**，不要比對名稱。 |
| `issueDate` | 發證日期 | **不保證是最初核發日**，見 §F |
| `oriIssueDate` | 原始發證日期 | 就是用來回答上一列那個問題的欄位 |
| `validDate` | 許可證有效期間終止日 | 監視期間以此為準（[docs/01](01-what-counts-as-new.md) 引藥品安全監視管理辦法第 2 條） |
| `licStatus` / `cancelDate` / `cancelReason` | 現行／已註銷狀態 | moiety 基線必須含已註銷證，見 [docs/04](04-moiety-first-appearance.md) |
| `ingredientsDesc` / `ingredientsDtoList` | 成分 | **是現況值，不是核發當時的快照**。成分欄會隨變更登記改寫，所以「發證日 + 成分」不等於「這張證核發時帶的成分」。實例與後果見 [docs/05](05-crosswalk.md) 第 3 筆 |
| `atcList` | ATC | 新分子常常是空的 |
| `monitorDate` | 「監視期限」 | **陷阱**：這是**醫療器材**欄位，藥品為 null。名字最像答案的欄位不是答案。 |

單筆示範工具：[`reference/tfda_lic_query.py`](../reference/tfda_lic_query.py)。

### 節流

主機在負載下回 `422`，訊息「連接次數過於頻繁」。那是**我方 IP 被限流**，
不是「這張證不存在」，也不是「這個標記消失了」。把 422 記錄成資料，會得到
一份假的空清單。

本 repo 逐筆引用明細 API 結果的許可證共 **11 張**（`M-44`），2026-08-05 以
**30 秒間隔**取得，過程中未觸發 422。工具預設就是這個節奏，且一次只吃一筆。

這個數字說的是「本 repo 引用了幾張證」，不是「你可以送幾次請求」。要查更多筆
是你的決定，也是你的責任——請自己加節流。

食藥署前端另有一個批次查詢端點，介面上看似公開了 `restraintItemsCode` 篩選
參數；以前端自己的 payload 原封送出兩次都回 **HTTP 400**，它不是一條可用路由。
本 repo 不公開它的路徑，也不在它上面建流程。

## D. 新成分新藥核准審查報告摘要

<https://www.fda.gov.tw/TC/siteList.aspx?sid=2712>

食藥署唯一以「新成分新藥」命名的逐案清單，每一列附一份審查報告 PDF。

| 量測（2026-08-05） | 值 | 登記 |
|---|---|---|
| 公告則數 | **206** | `M-10` |
| 展開後的許可證張數 | **273** | `M-11` |
| 其中存在於許可證資料 | **273 / 273** | `M-12` |
| 進入現行在案清單 | **256**（另 17 筆：15 張已註銷、2 張原料藥） | `M-13` |
| 中位發布落差（公告日 − 發證日） | **69 天** | `M-14` |
| 落差範圍 | −2,232 天 至 +1,093 天 | `M-15` |

落差的下界要小心：**−2,232 不是一個發布現象，是一個資料缺陷。** 那唯一一筆
公告日早於發證日的證是 衛部菌疫輸字第001082號，它的發證日欄位存的是換發日
（`M-21`，詳見 §F）。談「公告最多可以早幾天」時，這個下界不能拿來用。

**穩定度**：這個清單不是連續的。逐年公告則數為 2012 年 7、2013 年 2、2014 年 3，
接著 **2015、2016、2017 三年整年沒有任何公告**，2018 年才恢復（18 則），
之後的完整年度落在每年 15–32 則（`M-16`，2026 為部分年度）。任何以「多久沒新
公告」為條件的告警，門檻要用**月**為單位。

解析陷阱與逐筆真實樣本見 [docs/03](03-marker-nme-report.md)。

## E. 母體規模

| 量測（2026-08-05） | 值 | 登記 |
|---|---|---|
| 許可證總數（含已註銷） | **66,440** | `M-05` |
| 現行在案、`製劑`／`菌疫`、有發證日 | **19,705** | `M-06` |

19,705 是「現行藥品」的範圍；66,440 是 **moiety 基線**的範圍。兩者不可互換：
基線漏掉已註銷證，就會把老分子算成新藥（[docs/04](04-moiety-first-appearance.md)）。

`permit_type` 在原始資料裡以全形空白 U+3000 補齊（`製　劑`，長度 3）。
把 U+3000 直接貼進會經過 shell 的 SQL，會靜默失敗：篩選條件匹配不到任何列，
報告變成空的——那讀起來和「這週沒有新藥」一模一樣。用 `chr(12288)` 之類的
方式表達，不要貼字元。

## F. 日期欄位

| 欄位 | 覆蓋率（19,705 張現行證） | 登記 |
|---|---|---|
| 發證日期 | **19,705 / 19,705 = 100%** | `M-08` |
| 核准日期 | **286 / 19,705 = 1.5%** | `M-09` |

發證日那個 100% 是套套邏輯——「有發證日」本來就是這 19,705 張的篩選條件之一
（`M-06`），所以它必然是 100%，它不是資料品質的證據。有資訊量的是另一列：
照核准日排序會把清單縮成 286 列，所以任何面向讀者的日期都標**發證日**，
讓標籤和欄位一致。

但 `issueDate` **不保證是最初核發日**，見 [docs/06 §日期](06-permit-identity-and-dates.md#日期)
的 dupilumab 案例（`M-21`：四個獨立訊號指向 2018，欄位值卻是 2025）。

**這不是理論風險。** 拿 `issueDate` 當首見判定的排序鍵，已經讓本 repo 把那張證
判反，並據以寫出一段錯誤的法規解釋；逐筆說明見
[docs/05 第 6 筆](05-crosswalk.md)。要精確到單張證，用 `oriIssueDate`。

## G. 一個沒有用的「驗證」方法

`https://lmspiq.fda.gov.tw/web/DRPIQ/DRPIQ1000Result?licId=<licId>`

抓這個網址並讀 HTTP 狀態碼**證明不了任何事**。它是 client-side SPA 路由，
連食藥署自家資料裡的合法 licId 也回 404。要確認一張證存在，只能走 §C 的 API。

## H. 一個容易誤用的第四來源

食藥署開放資料另有一份「**監視成分**」清單。名字很像，但它是**成分層級**、
用於學名藥 BA/BE 要求的另一個概念，不是許可證層級的新藥清單。

**本 repo 沒有量測它**，所以這裡不給筆數也不給比對結果，只給一個可執行的判準：
拿 [docs/07](07-controls-and-pitfalls.md) 的四個具名新分子去查你手上的清單，
如果它們一個都不在裡面，你拿到的就不是新藥清單。

## 怎麼確認我沒搞錯

| 檢查 | 正控（必須成立） | 負控（必須不成立） |
|---|---|---|
| 碼表抓對了 | `Lic.Type` 回 61 筆、`Restraint.Dr` 回 91 筆 | 91 筆裡「監視」不只一個——若你只找到 1 個，是你的過濾器壞了 |
| 明細 API 通了 | `licBaseId=60001328` 回傳含 `07 新藥監視` | `licBaseId=01033862` 回傳只有 `["01 國 產"]` |
| 沒有把 422 當資料 | 422 時工具明講「這是限流」 | 422 時**不可**寫入「無此標記」 |
| 抓碼表有擋 HTTP 錯誤 | `curl --fail` 或等價的狀態碼檢查，錯誤時 exit 非 0 | 裸 `curl -s`：422 時仍 exit 0，把錯誤回應存成碼表 |
| 兩次請求之間有間隔 | `make codes` 等 30 秒才送第二次 | 兩條 `curl` 連著貼 |
| 數字帶得出出處 | 本頁每個數字都有 `M-NN`，查得到母體與重跑方式 | 一個沒有登記編號、也講不出母體的數字 |

`60001328` 是 IBALIZUMAB（新分子）；`01033862` 是一張 METRONIDAZOLE 學名藥證，
它同時是本 repo 最容易被誤判為正的負控——理由見 [docs/07](07-controls-and-pitfalls.md)。
