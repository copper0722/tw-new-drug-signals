# 05 — 三個訊號對起來看

**這頁回答什麼**：三個訊號在同一批藥上同不同意，不同意的地方為什麼不同意，
以及該選哪一個。這是整個 repo 最有用的一頁。

## 交叉表：食藥署清單 × moiety 首見

拿食藥署已公告、且仍在現行清單裡的 **256** 張證（`M-13`），對上自算的 moiety
首見旗標（`M-35`，量測 2026-08-05T14:33+08:00）：

| moiety 判定 | 張數 |
|---|---|
| 首見・單方 | 235 |
| 首見・複方 | 14 |
| **非首見** | **7** |
| 合計 | 256 |

**249 / 256 = 97.3%**（`M-36`）。

### 先講這個數字的效期

**這是那一次量測的記錄，不是現在的值。**

當時的首見判定以 `發證日期`（`issueDate`）為排序鍵。後來確認 `issueDate` 是
**現行證的發證日**，換發會把它往後推（[docs/06](06-permit-identity-and-dates.md)、
`M-21`），而下面第 6 筆正是被這件事害的。改用 `oriIssueDate` 需要逐證呼叫明細
API、每筆間隔 30 秒，本 repo 尚未把它納入首見計算，所以：

- 引用這個數字時，**連同「2026-08-05、以 `issueDate` 為鍵」一起引用**；
- **不要把它寫成當前值**，也不要拿它跟改用 `oriIssueDate` 之後的數字比較——
  那是兩個方法，兩個數字。

### 這個 97.3% 是單向的召回率，不是準確率

它只回答一件事：「食藥署說是新成分新藥的，自算法則抓到了幾成」。

反方向**完全沒有量測**。自算法則在整份清單上共旗標 **1,467** 張證（`M-37`），
其中被食藥署公告確認過的只有 249 張，**其餘 1,218 張沒有任何外部確認**
（`M-38`）。而且我們已經知道那裡面住著至少兩類偽陽性（包衣劑、同鹽異寫，見
[docs/04](04-moiety-first-appearance.md)）。

所以：**不要把 97.3% 當成這個旗標的準確率。** 它是召回率，而且分母是一個
被食藥署篩選過的、偏向真新藥的子集。

#### 這裡本來有一個算出來、但從來沒有被查證過的數字

早期版本寫的是「共旗標 1,472 張，其中只有 256 張被公告過，剩下 1,216 張沒有
外部確認」。**那個減法減錯了東西。** 256 是「已公告且仍在現行清單」的張數，
而上面那張交叉表自己就寫著：這 256 張裡有 7 張並沒有被旗標。該減的是 249。

兩個被減的數都是真的，差值卻從來沒有人去查。現在的 1,218 是**直接查出來的**
——「旗標為真、且不在公告清單裡」的列數——不是相減出來的。旗標總數同時從
1,472 降到 1,467，那是另一件事：清單在期間套用了日期更正（`M-42`），六張發證日
被截位的老證原本各自竊走了自己那個 moiety 的首見旗標。

留這一段是因為這個形態很常見也很難自己看見：**每一個成分都是真的，組合出來的
那個數字卻從來沒有被觀察過。** 遇到自己算出來的複合數字，去查一次它本身。

## 把七筆不一致逐一打開

**這七筆不是同一種東西。** 本 repo 早期版本說它們「全部是同一個分子的第二張
許可證」，那個概括只對其中三筆（第 1、2、7 筆）成立。另外四筆分別出自
**成分欄被改版**、量測基線、鹽別正規化與日期欄位，**其中兩筆根本不是「舊分子的
新劑量」**。逐筆打開才看得出來，這也正是這一頁存在的理由。

（第 3 筆的原因本身也改過一次。它一度被寫成「年度換株，正規化後與 2013 年那張
相同」——那句話用隨附的正規化器跑一次就會被推翻。一個概括被逐筆打開之後，
**打開的結果還是可以寫錯**；下面那一節連同可執行的反證一起放。）

逐筆的日期差距登記在 `M-39`：

是 2008-12-01（衛署藥製字第049838號），但含已註銷證後，最早的
LEUPROLIDE ACETATE 證是 衛署藥輸字第015389號，1986-09-24 發證、現已註銷。
讀這一欄時要記得它量的是「現行清單裡的最早」，不是分子真正的首見。

### 第 3 筆：不是正規化合併，是成分欄被改版

這一筆的原因很容易寫錯，而且錯法就在隨附程式的一次執行之內。早期版本寫的是
「年度換株，正規化後與 2013 年那張相同」。**用本 repo 自己的 `tw_moiety.py`
把兩張證的成分欄跑一次就能推翻它**：四個 moiety 裡三個相同、各有一個獨有
（`M-53`）——`B/PHUKET/3073/2013 - LIKE STRAIN`（衛署菌疫輸字第000939號）對
`B/PHUKET/3073/2013-LIKE VIRUS`（001230）。正規化沒有把任何字串合併。
兩張證的成分欄都收在
[`fixtures/ingredients.sample.jsonl`](../fixtures/ingredients.sample.jsonl)，
所以這個反駁你可以自己跑：

```console
$ python3 reference/measure_fixtures.py M-53
{"shared": 3, "only_2013": 1, "only_2023": 1}
```

真正的機制是**成分欄本身被改版**。衛署菌疫輸字第000939號 發證於 2013-04-24，
但它現在的成分欄裝的是 2022／2023 年的當季病毒株。所以「2013 年就有這個
moiety」是資料改版的產物，不是 2013 年的事實。

第六欄的 3,600 天量的是「現行清單裡，任一**共有** moiety 的最早發證日」
（與 `M-39` 的 SQL 一致），不是「moiety 集合相等」——那個最早日期來自被改版的
000939。

這一筆真正的教訓在下一節。

### 成分欄是現況欄位，不是核發當時的快照

[docs/06](06-permit-identity-and-dates.md) 用一整節講「發證日不保證是最初核發日」。
**成分欄有一模一樣的問題，而且方向更糟。**

許可證的成分欄會隨變更登記改寫，資料裡另有一個變更日期欄位記錄它最後一次被改的
時間。把一個**會被改版的成分欄**配上 `issue_date` 當首見鍵，等於宣稱這張證在
核發當天就帶著它今天的成分。流感疫苗是這件事最乾淨的案例：帶 2022 年病毒株的
現行證有 12 張，其中 **4 張的發證日早於 2020 年**，最早一張發證於 2010-09-20
（`M-54`）。

後果是**偽陰性**：一個 2023 年才出現的病毒株，會因為某張老證的成分欄被改版而
看起來「2013 年就有」，於是新的那張被判為非首見。這和 docs/04 已經列出的四種
噪音不同——那四種是字串層面的雜訊，這一種是**時間軸錯位**，正規化再仔細也擋不住。

要迴避它，得知道成分欄最後一次變更的時間；資料裡有這個欄位，但本 repo **沒有**
在母體規模上量測它與 `issue_date` 的關係，所以這裡只講機制，不給比例。

### 第 5 筆：鹽別不同，而正規化把它抹掉了

康紓維（Camcevi）的成分是 **leuprolide mesylate**；台灣既有的柳菩林一系列全部是
**leuprolide acetate**。食藥署為它出了一份新成分新藥核准審查報告（2023-12-05
公告），審查報告本身就把它當成不同的鹽處理。

而本 repo 的 moiety 正規化**刻意剝掉鹽別後綴**，於是 mesylate 與 acetate 都塌成
`LEUPROLIDE`，這張證就被判為非首見。**這不是雜訊，是這個方法的定義後果**：
剝鹽別讓 `DASATINIB MONOHYDRATE` 正確對回 `DASATINIB`
（[docs/04](04-moiety-first-appearance.md)），同一個動作也讓一個主管機關視為
有意義的差異消失了。同一條規則，兩個方向的效果。

早期版本把這一筆寫成「leuprolide 六個月劑型」、歸類到施行細則第 2 條第 2 款的
「改善療效時間」。**那是編出來的**：審查報告講的是鹽，本 repo 沒有任何證據說
食藥署是以改善療效時間認定它。已改。

### 第 6 筆：這張證根本不是「第二張」

杜避炎 300 毫克（衛部菌疫輸字第001082號）**本身就在新成分新藥清單上**，公告日
2018-12-05，而明細 API 的 `oriIssueDate` 是 **2018-05-10**（`M-21`）。現行清單裡
另一張 dupilumab 證是 衛部菌疫輸字第001133號（200 毫克，2020-07-20）。

**所以真正較早的是 001082，不是 001133。** 它之所以被判成非首見，只因為排序用的
`issueDate` 是 2025-01-14 ——那是**換發日**，不是最初核發日
（[docs/06](06-permit-identity-and-dates.md)）。這一筆完全是日期欄位造成的，
與劑量、劑型、法規分類都無關。

早期版本把它寫成「dupilumab 既有分子的新劑量」，並在多處引用「最早為 2020、
相隔 1,639 天」。**兩個說法都錯**，而且錯的方向一致：把一個資料缺陷讀成了一個
法規現象。分類的說法已改，那個 1,639 天則是直接刪掉——它不是一個量錯的間隔，
它是一個不存在的間隔。

## 這七筆在法規上是不是新藥？別問 `07`，答案在它們的出身

先講一件因為表格切法而容易被忽略的事：**這七筆本來就全部是食藥署公告過的
新成分新藥**——這張交叉表的母體就是「已公告且仍在現行清單裡的 256 張證」，
七筆是其中被自算法則判為非首見的那些。所以「它們是不是新藥」這個問題，
**食藥署已經逐案審查認定並公告過了**，不需要再從別的欄位推。

自算法則說它們「不是新 moiety」，那個敘述在字串層面也沒錯。兩邊都對，因為
兩邊量的不是同一件事。

那 `07` 呢？2026-08-05 逐筆查明細 API，七筆全部帶 `07 新藥監視`（`M-40`）：

| 許可證 | `restraintItemsCode` |
|---|---|
| 衛部菌疫輸字第001201號 | `02 輸 入`, **`07 新藥監視`**, `5G 小兒/少數嚴重疾病藥品認定` |
| 衛部菌疫輸字第001209號 | `02 輸 入`, **`07 新藥監視`**, `1D 須執行風險管理計畫` |
| 衛部菌疫輸字第001230號 | `02 輸 入`, **`07 新藥監視`**, `5F 免除銜接性試驗` |
| 衛部藥輸字第027899號 | `02 輸 入`, **`07 新藥監視`** |
| 衛部藥輸字第028546號 | `02 輸 入`, **`07 新藥監視`**, `5F 免除銜接性試驗` |
| 衛部菌疫輸字第001082號 | `02 輸 入`, **`07 新藥監視`**, `5F 免除銜接性試驗`, `68 …` |
| 衛部菌疫輸字第001309號 | `02 輸 入`, **`07 新藥監視`**, `5F 免除銜接性試驗`, `68 …` |

**7 / 7。** 這個 7/7 能講什麼、不能講什麼，要分開：

**能講的**：`07` 在這七筆上與食藥署的公告一致。也就是說，自算法則漏掉的這七張，
`07` 一張也沒漏。對「產生候選清單」這個用途來說，這是 `07` 的強項。

**不能講的**：不能反過來說「因為它們帶 `07`，所以它們是法定新藥」。第 7 條的
身分來自審查認定，不是來自一個限制項目碼；這七筆之所以確定是新藥，是因為
**食藥署公告過**，不是因為明細裡有 `07`。把因果反過來寫，就是把一個沒有公開
收錄準則的碼當成法律判準（[docs/02 §語意](02-marker-restraint-07.md#語意07-的觀察範圍)）。

**也不能講的**：不能替這七筆各自指定一個施行細則第 2 條第 2 款的分支。早期版本
就這樣做過——說 dupilumab 300 毫克是「改變使用劑量」、leuprolide 是「改善療效
時間」——而上面兩節已經證明那兩筆根本不是那回事（一筆是鹽別、一筆是日期欄位）。
**審查報告寫了什麼就是什麼；沒寫的不要替它補。**

真正的結論比較樸素：這七筆不是計數雜訊，它們是主管機關認定過的新藥；自算法則
沒抓到，不是因為它們不重要，而是因為它量的是字串首見，不是法規身分。

## 結論

**食藥署的清單是逐案審查認定後公告；自算的是正規化字串的首見。兩者都沒錯，
也不能互相取代。**

- 要「食藥署認定的新成分新藥」→ 用清單，接受 69 天落差（`M-14`）。
- 要「這個月核准了什麼、其中哪些帶新藥監視」→ 用 `07`，接受它的收錄準則未公開。
- 要「這個正規化 moiety 字串是不是第一次」→ 自己算，接受它是候選而非結論，
  而且它回答的不是「這個分子在台灣是不是第一次」（第 5 筆就是差在這裡）。
- 要一份可以發表的清單 → 三個都算，**把不一致逐筆打開**，就像這一頁做的。

而逐筆打開的價值，這一頁自己示範了：七筆裡有兩筆的原因，跟「新藥」的法規分類
完全無關（一筆是鹽別正規化，一筆是日期欄位選錯）。只看一個 97.3%（`M-36`），
這兩個缺陷永遠不會現形。

## 怎麼確認我沒搞錯

| 檢查 | 正控（必須成立） | 負控（必須不成立） |
|---|---|---|
| 交叉表加得起來 | 235 + 14 + 7 = 256（`M-35`） | 合計不等於已公告且在現行清單的張數 |
| 不一致有逐筆打開 | 七筆的**原因各自寫出來**，不是共用一句概括 | 「七筆全部是同一分子的第二張證」這種一次蓋七筆的說法 |
| 召回率沒被說成準確率 | 文中明講 1,218 張旗標未被外部確認（`M-38`） | 把 97.3% 寫成「這個旗標 97.3% 準確」 |
| 百分比帶著方法 | 引用 97.3% 時同時寫出 2026-08-05 與「以 `issueDate` 為鍵」 | 把它當成當前值 |
| 沒有替審查報告補分類 | 只寫審查報告與明細裡查得到的事 | 替某一筆指定「改變使用劑量」「改善療效時間」等款別 |
| 基線講清楚 | 「現行清單裡同 moiety 最早」與首見旗標的基線分開講 | 兩個基線混用，把 0 天當成真的同日 |
| 複合數字有被查過 | 「未經確認的旗標數」是查出來的（`M-38`） | 拿兩個真數字相減，卻沒查過差值本身 |
| 壞欄位算出來的間隔沒有留著 | 第 6 筆的「相隔幾天」欄留空並說明理由 | 照樣填一個從換發日算出來的天數 |
| 解釋沒有被隨附程式當場證偽 | 第 3 筆的原因跑 `measure_fixtures.py M-53` 會得到 `shared=3`，與文中一致 | 寫「正規化後兩張相同」，而隨附的正規化器說不相同 |

倒數第二列與最後一列都是本 repo 自己犯過的錯。原本這裡放的是另一個教訓
（一個**類別**解釋成立，不代表隨手加上的**時間**描述也成立）——那句話仍然對，
但這次的錯更基本：**那個類別解釋本身就有兩筆是錯的**。概括寫得越順，越少人
會去逐筆檢查。
