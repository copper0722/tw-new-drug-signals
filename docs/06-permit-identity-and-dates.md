# 06 — 許可證的身分與日期

**這頁回答什麼**：怎麼從許可證號組出 licId（以及兩個會產生**錯誤連結**的實作
細節）、為什麼不能用抓網頁來驗證它，還有日期欄位到底在說什麼。

---

## licId 的組成

```
licId = <2 位字別碼> || <序號原樣，不足 6 位才補零到 6 位>
```

字別碼取自 61 筆的 `Lic.Type` 碼表（`M-01`，[docs/00 §B](00-sources.md)）。例：

| 許可證號 | 字別 | 碼 | 序號 | licId |
|---|---|---|---|---|
| 衛部藥輸字第027899號 | 衛部藥輸 | 52 | 027899 | `52027899` |
| 衛部菌疫輸字第1082號 | 衛部菌疫輸 | 60 | 001082 | `60001082` |
| 衛部藥輸字第R00108號 | 衛部藥輸 | 52 | R00108 | `52R00108` |

**R 開頭的序號本身已經是 6 字元，永不補零。** 補成 `R000108`（7 字元）之後，
licId 會變成 `52R000108`——9 字元，而正常的 licId 是 8 字元。

參考實作 [`reference/tw_permit_id.py`](../reference/tw_permit_id.py)：

```console
$ python3 reference/tw_permit_id.py 衛部藥輸字第R00108號
衛部藥輸字第R00108號	52R00108	https://lmspiq.fda.gov.tw/web/DRPIQ/DRPIQ1000Result?licId=52R00108
```

## 兩個會靜默產生錯誤連結的細節

這是這個模組唯一的存在理由，值得寫進正文而不是註解。

1. **`regexp_replace` / `re.sub` 在不匹配時原樣回傳輸入**，不報錯。
2. **`lpad` 對超過目標長度的字串會截斷**（`lpad('0271234', 6)` → `'027123'`）。
   Python 的 `str.rjust` 不截斷，SQL 的 `lpad` 會。

兩者相加的後果：一個「只抓數字」的規則被放寬去容納 R 序號之後，如果沒有長度
守衛，就會把一段許可證號截成 6 字元當 licId 送出去。那會連到**另一張真實存在
的許可證**。

**一個錯的連結，比沒有連結更糟。** 沒有連結時讀者知道自己不知道；錯的連結
讓讀者以為自己在看正確的東西。所以參考實作在序號超過 6 字元時**丟例外**，
不截斷、不回傳猜測值，而且有一個測試專門釘住這件事。

## 一個沒有用的「驗證」方法

抓 `https://lmspiq.fda.gov.tw/web/DRPIQ/DRPIQ1000Result?licId=<licId>` 並讀
HTTP 狀態碼**證明不了任何事**。它是 client-side SPA 路由，連食藥署自家資料裡的
合法 licId 也回 404。

要確認一張證存在，只能走 [docs/00 §C](00-sources.md) 的明細 API，而那有節流成本。
所以：**licId 是給人點的連結，不是給機器做存在性檢定的。**

## 日期

### 用發證日，不要用核准日

| 欄位（19,705 張現行證，`M-06`） | 有值 | 登記 |
|---|---|---|
| 發證日期 | **19,705 / 19,705 = 100%** | `M-08` |
| 核准日期 | **286 / 19,705 = 1.5%** | `M-09` |

第一列的 100% 是套套邏輯（「有發證日」是這 19,705 張的篩選條件之一），有資訊量
的是第二列。照核准日排序會把清單縮成 286 列。所以面向讀者的日期一律標**發證日**，
讓標籤和欄位一致。藥品安全監視管理辦法第 8 條的五年報告期間也是從發證日起算
（[docs/01 §3](01-what-counts-as-new.md)），用詞一致有額外的好處。

### 但發證日不保證是「最初核發日」

這是一個本 repo 原本沒有量測、後來才補上的限制。

**衛部菌疫輸字第001082號**（杜避炎注射劑 300 毫克，dupilumab）：**五個佐證、
四種機制**都指向 2018，只有 `issueDate` 說 2025（`M-21`，n = 1）。

| 佐證 | 值 | 指向 | 機制 |
|---|---|---|---|
| 儲存的 `issueDate` | 2025-01-14 | 2025 | ← 有問題的那一個 |
| API 的 `oriIssueDate` | **2018-05-10** | 2018 | ① 上游自己另存的原始發證日 |
| 食藥署審查報告公告日 | **2018-12-05** | 2018 | ② 另一個來源（公告清單） |
| `validDate` | 2028-05-10 | 2018 | ③ 效期錨定在 2018-05-10 的週年（5 + 5 年，見下） |
| 序號鄰居 001081 | 發證 2018-04-25 | 2018 | ④ 序號依序核發 |
| 序號鄰居 001084 | 發證 2018-09-14 | 2018 | ④ 同上 |

**兩個鄰號是同一種機制的兩次應用，不是兩個獨立訊號。** 早期版本寫「四個獨立
訊號」，既數不出來也對不上這張表：它把兩個鄰號當成兩個機制，又漏算了 `validDate`。
三、四兩種機制的強度也不一樣——③ 是同一筆記錄裡另一個欄位的推論，④ 來自別的
許可證。逐項寫出來，讀者才判斷得了要相信到什麼程度。
順帶一提，那則審查報告是 273 筆裡**唯一**公告日早於發證日的一筆
（落差 −2,232 天，`M-15`；見 [docs/03](03-marker-nme-report.md)）——那個負落差
本身就是這個問題的警報。

**這不是一個無害的欄位差異，它已經製造過一筆錯誤結論。** 本 repo 的 moiety 首見
計算以 `issueDate` 排序，於是把這張證排在 2020 年那張 200 毫克證（衛部菌疫輸字
第001133號）後面，判為非首見，並在 [docs/05](05-crosswalk.md) 被寫成「既有分子的
新劑量」。改用 `oriIssueDate` 之後，它是較早的那一張。逐筆說明見
[docs/05 第 6 筆](05-crosswalk.md)。

**換發還會拿走另一個線索**：換發時 `old_permit`（前證號）不必然留下值，這張就是
空的。所以「有沒有前證號」不能用來偵測換發。

母體層級目前只有兩個**代理指標**（`M-43`，2026-08-05 量測於全部 66,440 張
（`M-05`）裡有發證日者）：

| 這個指標實際量的是什麼 | 張數 | 比例 |
|---|---|---|
| 發證日早於同字別前一個序號的證 | 4,066 / 66,413 | 6.1% |
| 發證日到有效期間終止日短於 5 年的證 | 1,825 / 66,439 | 2.7% |

**這兩個數字不能用來估計換發率，本 repo 也不再拿它們做任何推論。** 早期版本用
它們推出「絕大多數許可證的發證日仍然是最初核發日」，那個推論已刪除：一次換發
可以完全維持序號順序（換發不改序號），也可以帶任何長度的有效期間，所以兩個代理
指標對「這張證的 `issueDate` 是不是最初核發日」都沒有辨別力。用一個量別的東西的
指標去圍另一個量，就是量了個寂寞。

第一列的分子分母也換過：早期版本印的是 4,037 / 66,267，那組數字用任何寫得出來
的查詢都重現不出來。上面這組是重新量的，SQL 寫在 `M-43` 裡。百分比一樣是 6.1%，
但**一個寫得出查詢的 6.1% 和一個寫不出來的 6.1% 不是同一種東西**——後者只是一個
看起來很具體的字串。

**所以母體層級的答案是：不知道。** 手上逐筆查過明細的只有 11 張證（`M-44`），
其中 1 張不一致（就是上面那張）。11 張說不出母體比例，所以這裡不給比例。要真的
量它，成本是每張證一次 API 呼叫加 30 秒節流。

實務上的結論不受影響，而且很簡單：**排序或首見判定要精確到單張證時，
`oriIssueDate` 才是該用的欄位。**

### 不可能的發證日：七張證，以及怎麼處理才不算偷改資料

有些許可證的發證日**和它自己的許可證號互相矛盾**：號碼的鄰居都落在 1970–1999，
它的發證日卻落在 1911–1945。

| 量測（2026-08-05） | 值 | 登記 |
|---|---|---|
| 全部 66,440 張中，發證日早於 1930 年 | **27 張** | `M-41` |
| 其中在 19,705 張現行清單裡 | **5 張** | `M-41` |
| 改用「與同字別鄰近序號矛盾」為判準，現行清單裡 | **7 張** | `M-42` |
| 最早值 | 1911-01-03（衛署藥製字第033431號，已註銷） | `M-41` |

這些日期不是解析錯誤：直接向明細 API 查 `01033862`，它回傳的
`issueDate` 就是 `1911-03-23`。**上游資料本身如此。**

#### 用鄰號推，不要用猜的

序號是依序核發的，所以**同一字別、序號相鄰**的許可證，發證日應該相近。這給了
一個不必臆測的檢定方式。七張裡，六張可以據此得到有證據的更正值，第七張不行
（`M-42`）。

| 許可證 | 來源值 | 更正值 | 信心 | 依據 |
|---|---|---|---|---|
| 衛署藥製字第033862號 | 1911-03-23 | 1991-03-23 | mechanism | 民國年十位數遺失（80→0）；月日不變，鄰號 033854 為 1991-03-21、033865 為 1991-03-25 |
| 衛署藥製字第013923號 | 1917-11-28 | 1977-11-28 | mechanism | 66→6；鄰號 013912 與 013927 皆為 1977-11-28 |
| 衛署藥製字第041985號 | 1918-03-05 | 1998-03-05 | mechanism | 87→7；後一號 041987 為 1998-03-05 |
| 衛署藥製字第043181號 | 1919-08-23 | 1999-08-23 | mechanism | 88→8；鄰號 043180 與 043182 皆為 1999-08-23 |
| 內衛成製字第001169號 | 1920-10-08 | 1970-10-08 | mechanism | 59→9；下一號 001170 為 1970-10-08，且 1970 落在內衛（1971 改制前）年代內 |
| 衛署藥製字第007280號 | 1945-09-08 | 1975-09-08 | **inferred** | 月日不變且落在 007266（1975-08-29）與 007341（1975-09-13）之間；年份偏差不是單純截位，所以信心低於前五張 |
| 衛署藥製字第045960號 | 1970-09-30 | **不更正** | — | 月日對不上任何鄰號，沒有可推的依據。留著不解，比給一個猜出來的值好 |

**前五張的形態一模一樣：月日與來源完全相同，民國年少了十位數。** 那不是隨機
壞值，是某一次轉換裡的一個截位。同一個機制、五個受害者。

另有 衛部藥陸輸字第000618號，發證日 2013-07-18——早於衛福部成立五日。看起來是
改制交接期的產物，性質與上面七張不同，本 repo 不歸為同一類，也不更正。

#### 保留來源、另存更正、記錄依據

這一段的處理方式本 repo 改過。早期版本寫的是「量測過，刻意不修，傷害為零」，
那句話現在收回，因為它同時押了兩個沒有根據的東西。

現在的作法是三件事分開：

1. **來源值不動。** 鏡像就是鏡像；改了它，你手上那份就不再是上游說的話。
2. **更正值另存**，放在一張只讀的對照表裡，在**讀取時**套上去，不回寫來源。
3. **信心與依據逐筆記錄。** `mechanism`（看得出截位機制、月日吻合）與
   `inferred`（只有鄰號區間支撐）是兩種強度，不要壓成一個「已修正」。沒有依據
   的那一張就明確標成未解決。

「傷害為零」那句話也要收回，而且收回的理由比原本想的硬：**位移是量得到的。**

六張有更正值的證，每一張的**來源日期都早於現行清單裡同 moiety 的所有其他證**，
而更正後的日期都不是最早的（`M-52`，6 / 6）：

| 現行清單裡的受影響證 | 來源發證日 | 更正後 | 同 moiety 其他證最早 |
|---|---|---|---|
| 衛署藥製字第033862號（METRONIDAZOLE） | 1911-03-23 | 1991-03-23 | 1969-05-16 |
| 衛署藥製字第013923號 | 1917-11-28 | 1977-11-28 | 1970-06-04 |
| 衛署藥製字第041985號 | 1918-03-05 | 1998-03-05 | 1973-11-19 |
| 衛署藥製字第043181號 | 1919-08-23 | 1999-08-23 | 1969-04-01 |
| 內衛成製字第001169號（IODINE） | 1920-10-08 | 1970-10-08 | 1970-04-10 |
| 衛署藥製字第007280號 | 1945-09-08 | 1975-09-08 | 1969-06-16 |

換句話說：帶著來源日期，這六張每一張都會排到自己那個 moiety 的最前面；換上更正
值，一張也不會。**這正是「竊走首見位置」這個機制的直接量測，不是推想。**

原本的證據是「同 moiety 次早全部落在 1969–1973，所以受影響的都是幾十年前的老藥」
——那個觀察仍然成立，但它說的是**這一次的受害者不重要**，不是**沒有受害者**。
機制還在，而且已經在動：下一次同樣的截位落在一個真的新分子上，就會安靜地吃掉
一個新藥，而且沒有任何欄位會抗議。

（`M-52` 的範圍要講死：這是相對於**現行清單**的排序，不是相對於首見旗標真正的
基線——那個基線含已註銷證。所以它證明的是「來源日期會讓這張證排到同 moiety 的
最前面」，不是「它一定拿走了旗標」：一張更早的已註銷證仍然可能擋在前面。）

順帶一提，衛署藥製字第033862號 同時是 [docs/02](02-marker-restraint-07.md) 的
限制項目負控——一張學名藥證，既示範了日期陷阱，也示範了 `07` 的正確缺席。

## 怎麼確認我沒搞錯

| 檢查 | 正控（必須成立） | 負控（必須不成立） |
|---|---|---|
| 補零規則 | `衛部菌疫輸字第1082號` → `60001082`（8 字元） | `衛部藥輸字第R00108號` → `52R000108`（9 字元，序號被補成 7 位） |
| 有長度守衛 | 7 位序號**丟例外** | 回傳 `027123` 這種截斷值 |
| 沒有用網頁狀態碼驗證 | 存在性檢定走明細 API | 用 `DRPIQ1000Result` 的 404 當「不存在」 |
| 日期欄位標對 | 頁面寫「發證日」 | 寫「核准日」但取的是發證日欄位 |
| 知道發證日的限制 | 對 衛部菌疫輸字第001082號 這類證，用 `oriIssueDate` | 假設 `issueDate` 一律是最初核發日 |
| 沒有拿代理指標估換發率 | 明講母體換發率未量測（`M-43`） | 用序號倒置率或有效期間長度推出「大多數是最初核發日」 |
| 更正有依據且分級 | 每一筆更正都寫得出鄰號證據，信心分 mechanism／inferred（`M-42`） | 沒有依據的那一張也給一個猜測值 |
| 來源值沒被改掉 | 來源值保留，更正值另存、讀取時套用 | 直接把 1911 改寫成 1991 |
| 沒有宣稱「傷害為零」 | 位移有量出來（`M-52`），並講清楚它的基線範圍 | 用「受害者都是老藥」推出「這類缺陷無害」 |

前兩列在 [`reference/tests/test_permit_id.py`](../reference/tests/test_permit_id.py)
裡是可執行的。
